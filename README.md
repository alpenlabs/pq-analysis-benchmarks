# stark-boolean-verifier

Reproducible measurements of the verifier for the final compressed STARK proof
of three zkVMs: Risc0., SP1 and Stwo, and for SP1's shrink proof, a smaller
one its prover computes but does not return.

Versions are pinned. Proof artifacts are committed under `artifacts/`, so
every step except proving runs without a prover toolchain.

## Results

Proof size is the bytes a verifier needs beyond the public inputs (Risc0:
seal, control ID and its inclusion proof; SP1: shard proof without its
public values, recursion vk and its Merkle proof; Stwo: the leaf circuit
proof, its circuit hash and preprocessed root; SP1 shrink: the same three
components of the shrink proof). Gate counts are per verification under the Boolean cost model
described in the last section; "nonfree" is the count under free-XOR and
"total" adds the XOR gates. Each system appears as deployed and with its
hash replaced by BLAKE3. The daggered rows are not what a system's API
returns: see the footnotes under the table. The last row is the baseline: g16ckt's Groth16
(BN254) verifier with one public input and a compressed proof (in-circuit
decompression included), measured in the same model; the last column is
the ratio of nonfree gates to it. Exact counts, the XOR gates and the
uncompressed-proof Groth16 figures are in `results/gates.json`. The table
is generated by `gates.py` from `results/` and checked in CI.

Layout: `risc0/`, `sp1/`, `stwo/` hold one Rust workspace each;
`gadgets/` measures the Boolean gate costs.
Instrumentation of third-party crates is kept as patch files
(`<workspace>/patches/`) and applied by `<workspace>/patch.sh` to the
unmodified upstream sources (the crates.io crates for Risc0 and SP1, a
checkout of the pinned git revision for Stwo), which Cargo then uses via
`[patch]`.
`just check` re-derives everything under `results/` from the committed
artifacts (including `results/sp1/shrink/`, from the committed shrink proofs). Each run first checks the artifact is the one it claims to be:
Risc0 receipts are verified against the image ID and SP1 verifying keys
against the key hash recorded in `artifacts/manifest.json` (written by
`prove`, reproducible by building the guest sources), and the Stwo leaf's
output preimage must name the Blake program hash of the committed
`stwo/programs/<guest>/compiled.json`. `results/<system>/ops.json` is the operation ledger of one
verification and `results/<system>/params.json` the proof-system parameters
the verifier is compiled with; `gates.py` converts the three ledgers to a Boolean-gate
estimate (`results/gates.json`).

## Parameters

The rows above are the systems as shipped; nothing is normalised to a common
security level. The parameters each verifier is compiled with, read from the
pinned crates by `params` in each workspace (`results/<system>/params.json`),
are:

<!-- gates.py: params start -->
| verifier | field | rate | queries | fold | PoW bits | trace log size | stated security |
|---|---|---:|---:|---:|---:|---:|---|
| risc0 3.0.5 | babybear^4 | 1/4 | 50 | 16 | 0 | 18 | 97 bits, conjectured |
| sp1 6.3.1 | koalabear^4 | 1/4 | 124 | 2 | 16 | 20 | 100 bits, unique decoding |
| sp1 6.3.1, shrink | koalabear^4 | 1/8 | 94 | 2 | 22 | 18 | 100 bits, unique decoding |
| stwo 49f8e037 | m31^4 | 1/2 | 70 | 16 | 26 | 23 | 96 bits, conjectured |
<!-- gates.py: params end -->

"Stated security" is the figure the project's own source attaches to these
parameters, on the basis it names. Risc0's 97 bits and Stwo's 96 bits are
conjectured (Stwo's is `pow_bits + log_blowup * queries`); SP1 sizes its
query count for 100 bits under the unique-decoding bound, which needs no
conjecture and is why it uses 124 queries at the same rate Risc0 covers with
50. Trace log size is the recursion or leaf circuit's trace for the measured
proof (Risc0: po2 in the seal; SP1: the compressed stage's stacking height;
Stwo: the leaf verifier circuit, wrapping a Cairo trace of log size 25). The
three fields are all 31-bit primes with a degree-4 extension. The 124 SP1
queries are also the 124 `pow` calls in its ledger.

## Risc0

Install the Risc0 toolchain (`rzup`, providing `r0vm` 3.0.5) following
https://dev.risczero.com/api/zkvm/install. Then:

```sh
cd risc0
cargo run --release -p host -- prove <guest>   # writes artifacts/risc0/<guest>.bin
cargo run --release -p host -- size <guest>    # size breakdown of that receipt
```

Guests: `trivial` (commits one `u32`), `fib` (a few million cycles, several
segments), `journal` (commits 4 KiB). `size` needs only stable Rust and the
committed receipts.

```sh
./patch.sh                                     # once; fetches risc0-core 3.0.2 and applies patches/
cargo run --release -p host -- count <guest>   # writes results/risc0/ops.json
```

`count` verifies the receipt and writes an operation ledger. Poseidon2
permutations are counted by a `poseidon2` hash suite injected through
`VerifierContext`, per `HashFn`/`Rng` method, without modifying the
verifier (`risc0/host/src/count.rs`). BabyBear operations are counted by
`patches/risc0-core-3.0.2.patch`, which adds a counter to each `Elem`
operator impl and to `pow`/`inv` (extension-field operations decompose
into base operations; Montgomery conversions are not counted). The hash
suite snapshots the counters around every call it forwards, so the ledger
separates `in_hash_suite` (the permutations, which are BabyBear arithmetic
themselves) from `residual` (the rest of the verifier) by measurement;
`mul_per_permutation` must come out an integer. The multiplications inside
`pow` are recorded separately as `pow.mul`: `pow` is square-and-multiply and
the verifier raises generators to Fiat-Shamir derived query positions, so
that number (about 38 thousand, of which 450 `inv` calls at a fixed 61 each
are 27,450) varies with the seal by a few hundred, while `residual` does not.
The gate estimate prices `pow.mul` together with `residual`: the verifier
circuit's only input is the proof, so inversions and exponentiations are
computed in-circuit rather than supplied as witnesses. Poseidon2 is the hash
the shipped verifier uses; the split is what allows a different hash to be
costed in its place. The ledger is the same for every guest, since the
succinct receipt proves the fixed recursion circuit; CI compares each
guest's output against the committed file with `ledger_diff.py`, which
requires an exact match except for `pow.mul`, allowed to differ by 2%.

## SP1

Install the SP1 toolchain (`sp1up`, providing `cargo prove`) following
https://docs.succinct.xyz/docs/sp1/getting-started/install. Then:

```sh
cd sp1
cargo run --release -- prove <guest>   # writes artifacts/sp1/<guest>.{bin,vk}
cargo run --release -- size <guest>    # size breakdown of that proof
```

Guests: `trivial` (commits one `u32`), `fib` (a few million cycles, proved
with a 2^22-cycle shard size so it spans several shards), `journal` (commits
4 KiB). Proving runs the CPU prover in-process. `size` needs only stable
Rust and the committed artifacts (build with `SP1_SKIP_PROGRAM_BUILD=true`
to skip the guest build); `sp1-prover-types` needs `protoc` on the path.

```sh
./patch.sh                              # once; fetches the pinned Plonky3 crates and applies patches/
cargo run --release -- count <guest>    # writes results/sp1/ops.json
```

`count` verifies the proof with `LightProver` and writes the operation
ledger. SP1 has no hash-suite injection point, so the counters are patches
to the Plonky3 crates it uses: `p3-field` holds the counters and instruments
`exp_u64_by_squaring`; `p3-koala-bear` counts `Add`/`Sub`/`Mul`/`Sum` and
`try_inverse`; `p3-symmetric` and `p3-challenger` count the permutations
performed by `TruncatedPermutation::compress`, `PaddingFreeSponge` and
`DuplexChallenger`, and attribute the field operations inside each to the
hash. The ledger has the same shape as Risc0's, with `mul_per_permutation`
(296 for this Poseidon2: width 16, `x^3`) as the integrality check.
KoalaBear's `try_inverse` is a fixed chain of 29 squarings and 7
multiplications rather than a call to `pow`, so its multiplications are in
`residual` (`inv_calls` counts the calls); `pow.mul` holds only the
multiplications inside `exp_u64_by_squaring`, one call per FRI query, which
vary with the proof and are priced like Risc0's.

### Shrink

The compressed proof is not the smallest KoalaBear proof SP1 produces. Its
pipeline is core, compress, shrink, wrap, Groth16: shrink verifies the
compressed proof in a smaller recursion machine
(`RecursionAir::shrink_machine`, log stacking height 18 against 20) at rate
1/8 with 94 queries and 22 bits of grinding, against the compressed proof's
1/4, 124 queries and 16 bits; wrap then moves to BN254, and its proof is
larger than either. `sp1-prover` runs shrink inside `run_shrink_wrap` and
feeds it straight to the wrap prover, so neither the SDK nor the worker API
returns it. `patches/sp1-prover-6.3.1.patch` widens `ShrinkProver::{prove,
verify}` to `pub`; nothing else about the stage is changed.

```sh
cargo run --release -- shrink <guest>         # artifacts/sp1/<guest>.shrink.bin, artifacts/sp1/shrink.vk
cargo run --release -- shrink-size <guest>    # results/sp1/shrink/size.json
cargo run --release -- shrink-count <guest>   # results/sp1/shrink/ops.json
cargo run --release -- shrink-params <guest>  # results/sp1/shrink/params.json
```

`shrink` reads the committed compressed proof, so only the shrink stage is
proved; it needs a prover but no guest toolchain, and can be re-run without
re-proving (`just shrink-sp1` does all three guests). The other three read
what it wrote and run in CI from the committed artifacts, like every other
measurement here.

Each of the three first verifies the shrink proof through
`SP1Verifier::verify_shrink`, which checks the shard proof against the shrink
verifying key, that key's membership in SP1's recursion vk tree, the
public-values digest and `vk_root`, `is_complete`, and that `sp1_vk_digest`
is the guest's. That last check is what ties the shrink proof to a particular
guest, whose verifying key is in turn checked against `artifacts/manifest.json`.

The shrink verifying key is a constant of the proof system, but unlike the
wrap key SP1 ships no copy of it, so `shrink` writes out the one its prover
derives and records its hash in `artifacts/manifest.json` alongside the guest
keys. A reproducer does not have to take that file on trust: the proof's
`vk_merkle_proof` shows the key is a member of SP1's recursion vk tree, whose
root ships as a constant inside `sp1-verifier`, so SP1's own released data
pins which key is the right one. The manifest entry only catches a swapped
file earlier, with a clearer error.

Proof size and verifier cost do not move together across the last two stages.
Compress to shrink makes both smaller. Shrink to wrap makes the proof larger
in bytes, because a BN254 element is 32 bytes where a KoalaBear element is 4,
in exchange for a verifier a BN254 circuit can express cheaply. That trade is
worth taking for an on-chain Groth16 verifier and not for a Boolean one, which
is why shrink is the end of the line measured here.

## Stwo

The guests are Cairo 0 programs (`stwo/programs/<guest>/<guest>.cairo`),
committed together with their `compiled.json` so only Rust is needed to
prove. To recompile one:

```sh
uvx --from cairo-lang==0.14.0.1 cairo-compile --proof_mode \
    programs/<guest>/<guest>.cairo --output programs/<guest>/compiled.json
```

The prover crates are pinned to a revision of `starkware-libs/proving`, the
monorepo that superseded `stwo-cairo` in July 2026. The Rust toolchain is
pinned by `stwo/rust-toolchain.toml` and installed by rustup on first use.

```sh
cd stwo
RUST_MIN_STACK=8388608 cargo run --release -- prove <guest>   # writes artifacts/stwo/<guest>.bin
RUST_MIN_STACK=8388608 cargo run --release -- size <guest>    # size breakdown of that proof
```

Guests: `trivial` (writes one value to the output), `fib` (100,000
recursive steps), `journal` (writes 1,024 values to the output). Parameters
for the flat proof are in `stwo/params.json` (`pow_bits` 26, blowup 2, 70
queries, `canonical_small` preprocessed trace, whose 2^20-row limit sizes
`fib`); the leaf proof below uses the registry's parameters instead.
The flat proof is one STARK over the whole execution, so its size scales
with the populated AIR columns. The constant-size artifact is the leaf
circuit proof of upstream's recursion: the guest runs as a task of the leaf
bootloader (`stwo/leaf/`), its Cairo proof is verified inside the leaf
verifier circuit, and that circuit is proved. The circuit is fixed by the
registry (`stwo/leaf/circuit_registry.json`): upstream's production
registry, generated with its `circuit-params --registry` over
`circuit_registry_definitions/production/definition.json` at the pinned
revision (about 6 minutes and 52 GB), which proves the Cairo run with the
full `canonical` preprocessed trace and lists leaf verifiers for Cairo trace
log sizes 25 to 29, all padded to one component shape. Every guest here
lifts to trace log size 25, so the leaf proof has the same size and circuit
hash for all of them.

```sh
RUST_MIN_STACK=8388608 cargo run --release -- wrap <guest>        # writes artifacts/stwo/<guest>.leaf.json
RUST_MIN_STACK=8388608 cargo run --release -- size <guest>.leaf   # size and verification
```

`wrap` needs about 50 GB of memory and takes about 2.5 minutes per guest.

```sh
./patch.sh                                                    # once; fetches the pinned proving revision and applies patches/
RUST_MIN_STACK=8388608 cargo run --release -- count <guest>   # writes results/stwo/ops.json
```

Upstream verifies a leaf circuit proof by building the verification circuit
for it (`circuit_verifier::verify_circuit`, in the same gate DSL the leaf
circuit is written in) and evaluating that circuit. The verifier therefore
already is a circuit, and `count` reads its gate counts off the finalized
`Circuit`: QM31 `add`/`sub`/`mul`/`pointwise_mul`/`eq`
gates and permutation gates on the field side, and on the hash side Blake2s
G-function gates (80 per 64-byte compression, which is the integrality
check), the `triple_xor` finalization and the `m31_to_u32` re-encoding at
the hash boundary. Unlike the Risc0 and SP1 ledgers, which count native
base-field operations of the shipped verifier code, this one counts gates
over the degree-4 extension; the gate estimate accounts for that.

The circuit also has `guess` wires: values the prover supplies, which the
circuit constrains but does not compute. `count` reports them under
`field.ops`. Of the 208,743 in this verification, 206,406 are the proof and
public inputs entering the circuit (`proof.guess` in
`circuit_verifier/src/verify.rs`; every Merkle path, FRI witness, query
sample and out-of-domain evaluation, with each 32-byte digest as sixteen
16-bit limbs) plus 1,530 bit decompositions of values already in the circuit
(query indices, sort keys, proof-of-work words). In a Boolean circuit whose
input is the proof, both are free: the former is the input itself and the
latter are the wires. The remaining 2,337 are inversion results: 23 `inv`
and 910 `div` in QM31, and 1,404 QM31 variables holding the 5,460 M31
inverses of the FRI folding twiddles, taken 70 lanes at a time by
`Simd::inv`. The circuit checks each with one multiplication and one
equality. `Simd::inv` is visible upstream only as guesses, so
`patches/proving-49f8e037.patch`, applied by `patch.sh` to a checkout of the
pinned revision that `Cargo.toml` substitutes for the git dependencies, adds
three counters to the `circuits` crate's `Stats`: calls, lanes (M31
inversions) and variables. Nothing else is changed. With the proof as the
circuit's only input these inverses must be computed in-circuit, and the
gate estimate prices them per element as stwo's own field code computes
them: 37 M31 multiplications for an M31 inverse (`pow2147483645`, 30
squarings and 7 products) and 53 for a QM31 inverse (four CM31 products of 3
M31 products each, plus a CM31 inverse of 41). The redundant hint checks are
left in the count.

## Gate estimate

```sh
python3 gates.py    # writes results/gates.json and prints the table
```

Gate costs come from `results/gadgets.json`, produced by the `gadgets/`
workspace with the gate-count instrumentation of
[alpenlabs/g16](https://github.com/alpenlabs/g16) (`g16ckt`, pinned by
revision in `gadgets/Cargo.toml`):

```sh
cd gadgets
cargo run --release    # writes results/gadgets.json
```

The model is free-XOR garbling: nonfree gates are the AND-type gates, XOR is
free but counted separately. BLAKE3 and the Groth16 verifier are g16ckt's
own gadgets. The rest is built in `gadgets/src/` from the same u32
primitives, each computing exactly what the pinned verifier computes and
following its code except in the two places noted below: BLAKE2s;
Montgomery multiply, modular add and subtract for BabyBear and KoalaBear;
Mersenne multiply, add and subtract for M31; QM31 add, subtract, pointwise
multiply and multiply; and the two Poseidon2 permutations, risc0-zkp's
(width 24, `x^7`, mirrored round by round from `poseidon2_mix`) and SP1's
(p3 Poseidon2 over KoalaBear, width 16, `x^3`, with p3-koala-bear's
specialised internal layer). Every gadget is checked against the native
implementation on several inputs before its count is recorded: the field
gadgets against the crates' arithmetic, the permutations against
`risc0-zkp` and `slop-koala-bear`, the hashes against the `blake3` and
`blake2` crates, the Groth16 verifier by accepting an arkworks proof. The
gadgets depart from the software in two places where the software's
layout is a CPU choice that no Boolean-circuit implementer would copy. The
QM31 multiplication gadget is Karatsuba at both extension levels (9 M31
products); stwo's own code is schoolbook (20 products, with `2 + i` applied
as a general product), about twice the gates. Both are measured, the table
uses Karatsuba and `results/gates.json` records the Stwo residual under the
other. In risc0-zkp's Poseidon2, the `M_EXT` multiplications by 2 and 4 are
doublings in the gadget where the software does Montgomery multiplications
by constants. Neither departure changes what is computed, only how, and
every gadget is still checked against the native result. This discount
reaches only Stwo's arithmetic: Risc0's and SP1's degree-4 extension
multiplications are priced as their code performs them (19 and 22 base
multiplications, schoolbook), because their ledgers count base-field
operations and never see an extension multiplication as a unit. Applying
Karatsuba there would need the extension multiplications counted
separately and is not modelled. For Risc0 and
SP1 the measured permutation gadget is also compared with the same
permutation priced per counted field operation (`hash_priced_from_ops`);
the two routes differ by up to a third, in opposite directions for the two
instances, which is why the permutation is measured rather than priced.

Each system is totalled under its deployed hash and under each of four
hashes (BLAKE3, BLAKE2s, and the two Poseidon2 instances), replacing each
hash unit (permutation or compression) one-for-one and keeping the field
arithmetic; a system's own hash reproduces its as-deployed total. The
one-to-one mapping is exact for Merkle nodes and approximate for sponge
absorbs and Fiat-Shamir, and other than the deployed hash it assumes a fork
of prover and verifier.

Every field operation the shipped verifier performs is priced, the
multiplications inside inversions and exponentiations included. The circuit
is meant to be evaluated with the proof as its only input, so nothing is
supplied as a witness: an inverse costs what the verifier's own code spends
computing it (61 multiplications for Risc0's `pow(P - 2)`, 36 for
KoalaBear's addition chain, 37 and 53 for stwo's M31 and QM31 routines), not
one multiplication and a check against a prover-supplied value. Stwo's
circuit takes its inverses as prover hints, so the estimate adds their
computation to its field cost (`inversions` in `results/gates.json`; see
[Stwo](#stwo)). Stwo's equality checks are counted in its ledger but not
priced, about 0.05% of its row; its permutation gates reorder columns by a
sort key that is a circuit constant and its `m31_to_u32` gates re-encode
field elements as 32-bit words, both of which are fixed rewiring in a
Boolean circuit and cost nothing.
